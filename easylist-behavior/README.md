# easylist-behavior

`easylist-behavior` records how easylist behaves as snapshots: hand-written fixtures (list definitions, filter expressions, and GraphQL operations) paired with outcome files generated by running them against a seeded PostgreSQL database. When a change alters behaviour, the outcome files change with it, so a reviewer sees the change in the diff as a fixture next to its new outcome, without reading the code.

The module exists only for its tests. Nothing imports it, and it is not published.

Snapshots complement the [conformance suite](../easylist-sqlpg/README.md#run-the-conformance-suite); they do not replace it. The conformance suite is the contract for drivers: it checks that every driver binds the same arguments, returns the same errors, and matches the same rows. Snapshots run through one driver, [easylist-sql-gorm](../easylist-sql-gorm), and describe what the library as a whole does with a list, a filter, or a GraphQL request.

## Layout

```
easylist-behavior/
  compose.yml          PostgreSQL 16 on port 54329, for local runs
  schema.sql           tables and enum types of the fixture database
  seed.sql             its rows; the header comment lists every person and what each relative time value matches
  lists/lists.go       the fixture lists, people and countries, and their Registry
  graph/               a gqlgen project with the easylist plugin; only gqlgen.yml, schema.graphqls, and resolver.go are hand-written
  cmd/generate/        the gqlgen entrypoint that go generate ./graph runs
  testdata/
    lists/<list>.golden                   outcome: the list's GraphQL SDL and operator matrix
    lists/shared.golden                   outcome: the SDL shared by all lists
    filters/<family>.txt                  fixture: filter cases of one operator family
    filters/<family>.golden               outcome: the rows each case matches, or its error
    filters/<family>.sql.golden           outcome: the SQL and arguments each case compiles to
    queries/<name>.graphql                fixture: one GraphQL operation
    queries/<name>.json                   outcome: the server's response
  *_test.go            the snapshot and coverage tests, all in the module root
```

## Start the database

The snapshot tests need PostgreSQL 16 and `EASYLIST_PG_DSN`. From the repository root, start the database in `compose.yml` and wait until it accepts connections:

```sh
docker compose -f easylist-behavior/compose.yml up -d --wait
export EASYLIST_PG_DSN='postgres://postgres@127.0.0.1:54329/postgres?sslmode=disable'
```

This is the same `EASYLIST_PG_DSN` that [easylist-sqlpg's README](../easylist-sqlpg/README.md#start-a-local-postgresql) documents, so one database serves both the snapshots and the conformance suite. If a database from that README is already running, use it instead: both listen on port 54329.

Stop and remove it when done, again from the repository root:

```sh
docker compose -f easylist-behavior/compose.yml down
```

Each test run creates its own schema, `easylist_behavior_<random>`, loads `schema.sql` and `seed.sql` into it, uses only that schema and the UTC session time zone, and drops it when the run ends. Several runs, and the conformance suite, can therefore use one database at the same time.

## Run the tests

From the `easylist-behavior` directory, run:

```sh
go vet ./...
EASYLIST_PG_DSN='postgres://postgres@127.0.0.1:54329/postgres?sslmode=disable' go test .
```

Without `EASYLIST_PG_DSN`, every test that computes an outcome skips with `EASYLIST_PG_DSN is not set`, and no outcome file is read or written, even with `-update`. The coverage tests and the harness's own unit tests still run. When the variable is set and the database cannot be reached, the tests fail. [CI](../.github/workflows/ci.yml) sets the variable and fails if any test skips for lack of it.

`TestGraphGeneration` regenerates a copy of `graph/` and fails if the committed generated files are stale. It runs gqlgen and `go build`, so it skips under `-short`.

## Refresh outcomes

When a test fails because an outcome changed, it names the outcome file and prints a line diff. If the new outcome is intended, rewrite the outcome files from the `easylist-behavior` directory:

```sh
EASYLIST_PG_DSN='postgres://postgres@127.0.0.1:54329/postgres?sslmode=disable' go test . -update
```

With `-update`, the tests write every outcome file, delete outcome files whose fixture no longer exists, and pass. Read the resulting `git diff` before committing it; it is what reviewers will read.

Name the package `.`, not `./...`. The `-update` flag is defined only by the tests in the module root, and `go test ./... -update` fails with `flag provided but not defined: -update` in any other package of the module that has tests.

`-run` works with `-update`: `go test . -update -run 'TestFilterSnapshots/null'` rewrites only `null.golden` and `null.sql.golden`. Orphaned outcome files are found from the fixture files that exist, not from the tests that ran, so a narrowed run never deletes another fixture's outcome.

## Add a filter case

A file `testdata/filters/<family>.txt` holds the cases of one operator family, such as `null`, `text`, or `relative-time`. Cases are separated by blank lines. A case is zero or more `#` comment lines followed by exactly one line holding the filter expression:

```
# != keeps NULL rows
active != TRUE

# BETWEEN with a list
age BETWEEN (30, 40)
```

Any other shape, such as two expressions in one case or a comment after the expression, fails the test with the file and line.

Each case runs on the `people` list at the pinned reference time, with the list's maximum page size, sorted by `id`, and selects `name` and every field the filter references. `<family>.golden` repeats the case and shows the count and the rows:

```
# != keeps NULL rows
active != TRUE
=> 7 rows
  id | name        | active
   2 | Bob Stone   | false
   4 | Dan O'Brien | NULL
   ...
```

A case that fails to parse or plan shows `=> error: <message>`, with the error's position, instead of rows. Values print as `NULL`, text and enums as they are, numbers in their exact text, dates as `2026-10-27`, timestamps as RFC 3339 in UTC, and arrays as `[a, b]`, with `[]` for an empty array.

`<family>.sql.golden` repeats each case that compiles, then its page and count queries with their arguments. Error cases are left out.

Add a case to the file whose family fits it, or add a new `<family>.txt` file for a new family, then refresh the outcomes. Use the people in `seed.sql`, whose header comment lists their values and which relative time values each one matches.

## Add a GraphQL request

Add `testdata/queries/<name>.graphql` holding one operation, with its arguments written inline; there is no variables file. The tests send it to the module's GraphQL server and write the response body, indented in the server's field order and with any `errors` member, to `<name>.json` beside it. Client time zones are exercised here, through the `timezone` argument of a list query, as in `timezone-today.graphql`.

## Change the fixture lists

`lists/lists.go` holds the lists `people` and `countries` and the `Registry` that the tests and the generated GraphQL code use. The package must import only `easylist-core`, because the generated code imports it. For every list, `testdata/lists/<list>.golden` holds the SDL the [easylist-gqlgen](../easylist-gqlgen) plugin generates for it and an operator matrix: for every field and every filter operator, `ok` or the error a request filtering that field with that operator is rejected with.

To add a field:

1. Add its column to `schema.sql`, and values for it to `seed.sql`. Keep the seed's header comment in step with the rows.
2. Add the field to the list in `lists/lists.go`.
3. Regenerate the GraphQL server from the `easylist-behavior` directory:

   ```sh
   go generate ./graph
   ```

4. Refresh the outcomes with `go test . -update`.

A new list also needs a query field in `graph/schema.graphqls` and a resolver in `graph/resolver.go`, like `countries`, before `go generate ./graph`. If you skip the regeneration, `TestGraphGeneration` fails.

## Coverage

Two tests make sure that the fixtures keep up with easylist. They need no database.

- `TestFieldTypeCoverage` fails when the fixture lists do not declare every field type both as a scalar and as an array, or lack a nullable, a non-nullable, a joined, or a calculated field.
- `TestFilterFeatureCoverage` fails when the filter fixtures, together with the `filter:` arguments of the GraphQL fixtures, do not use every predicate operator, both logical connectors, every time keyword, every duration unit, every arithmetic operator, and unary minus.

Both enumerate easylist's types and filter enums through their names, so a new field type or filter feature fails them until a fixture uses it, and each failure names what is missing. A new ability therefore cannot ship without a snapshot.

## Pinned time

Every snapshot runs at the reference time Tuesday 2026-10-27 10:00 UTC, the instant the conformance suite uses too. The runtime's `Clock` returns it, the database session time zone is UTC, and timestamps are read back in UTC, so outcomes are the same on any day and on any machine. The seed places its dates and times relative to that instant, so `TODAY`, `START_OF_WEEK`, and the others each match known people. The reference time is one constant, `refTime` in `harness_test.go`; changing it changes most outcome files.

## Review a change

Read the outcome diffs in this order:

1. `*.golden` and `*.json`, except `*.sql.golden`. These are behaviour: which rows a filter matches, which errors it gives, which operators a field accepts, and what a GraphQL client receives. Each diff hunk sits under the fixture it came from, so check that every change is one the pull request means to make.
2. `*.sql.golden`. This is implementation. When the SQL changes but the rows in the matching `.golden` file do not, the change is a refactor.

A behaviour change with no outcome diff means the fixtures do not cover it yet; ask for a case.
