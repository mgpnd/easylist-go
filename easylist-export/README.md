# easylist-export

`easylist-export` (package `easylistexport`) turns an `easylist.ExportRequest` into a CSV or XLSX file written to any `io.Writer`. Your application owns everything around it: the job queue, job status, and where files are stored. The usual flow is:

1. A client calls an export mutation generated by [easylist-gqlgen](../easylist-gqlgen) (or calls `Registry.ValidateExport` itself).
2. The validated request reaches your `easylist.Exporter`, which stores it as JSON in a queue or table and returns a job ID.
3. A worker decodes the request and calls `easylistexport.Run`.

## Write a worker

```go
type Worker struct {
	Registry *easylist.Registry
	Runtime  *easylist.Runtime
	Dir      string
}

// Handle runs one export job whose payload is a JSON-encoded easylist.ExportRequest.
func (w *Worker) Handle(ctx context.Context, jobID string, payload []byte) (path string, err error) {
	var req easylist.ExportRequest
	if err := json.Unmarshal(payload, &req); err != nil {
		return "", err
	}
	ext := ".csv"
	if req.Format == easylist.XLSX {
		ext = ".xlsx"
	}
	path = filepath.Join(w.Dir, jobID+ext)
	f, err := os.Create(path)
	if err != nil {
		return "", err
	}
	if err := easylistexport.Run(ctx, w.Registry, w.Runtime, req, f); err != nil {
		f.Close()
		os.Remove(path) // a failed export leaves an incomplete file
		return "", err
	}
	return path, f.Close()
}
```

`Run`:

- validates the request again against the current registry, because list definitions can change between enqueueing and running; a request that no longer validates fails before any row is written, with an error naming the problem, such as a removed field;
- runs exactly one query, with the list's scope, the request's filter and sort, and no limit or offset, and encodes each row as it is read, so memory use does not grow with the number of rows;
- evaluates requested calculated fields once per row with the worker's context;
- stops at the first query, calculated-field, encoding, write, or context error and returns it. Treat anything already written as incomplete.

A long export holds one database connection and one snapshot for its whole run.

## File contents

Both formats have one column per requested field, in request order, and a header row of field titles (a field's `Title`, or its name). NULL values are empty cells.

**CSV** is UTF-8 with comma separators and RFC 4180 quoting. Dates are `YYYY-MM-DD`, timestamps RFC 3339 in UTC, booleans `true`/`false`, numerics their exact decimal text, and enums their declared value.

**XLSX** has one worksheet named after the list (truncated to 31 characters). Strings are text cells and never formulas. Integers within ±2^53 and floats are number cells; numerics and larger integers are text cells, so no digits are lost. Dates and timestamps (in UTC) are date cells, and booleans are boolean cells. The workbook is built with excelize's `StreamWriter`, which keeps rows in temporary files rather than memory, and the zip is written to the writer when the export completes.

### CSV formula risk

CSV values are written unchanged. Spreadsheet tools can interpret a cell starting with `=`, `+`, `-`, or `@` as a formula, so a value like `=HYPERLINK(...)` typed by one user may run when another user opens the file. If exported data can contain such text and your users open CSV files in spreadsheet tools, prefer XLSX, whose text cells are never formulas.
